# Use Case Specifications — Login, Manage Accounts & Permissions

---

## UC: Login

**Primary actors:** System Administrator, Logistics & Resources Officer, Dispatcher, Field Commander, Field Crew Member
**Goal:** Authenticate the user and open the interface that matches the user's role.

### Details
**Pre-conditions**
1. The client application is running and connected to the server.
2. The user has an active account in the system.

**Post-conditions — success**
1. The user is authenticated and a session is opened for the workstation.
2. The system displays the main screen matching the user's role.
3. The login is recorded in the audit log.

**Post-conditions — failure**
1. No session is opened.
2. The failed attempt is recorded in the audit log.

### Flow of Events (main flow)
1. The user opens the login screen.
2. The user enters a username and a password.
3. The user submits the login request.
4. The system verifies that the username exists and that the account is active.
5. The system verifies the password against the stored salted hash.
6. The system identifies the user's role.
7. The system opens a session and displays the role's main screen.

### Extensions
- **2a. Empty field:** The system displays "Username and password are required" and returns to step 2.
- **4a. Unknown username or wrong password (also 5a):** The system displays "Invalid username or password" (without revealing which one is wrong), increments the failed-attempt counter and returns to step 2.
- **4b. Account deactivated by the administrator:** The system displays "Account is inactive — contact the system administrator". The use case ends in failure.
- **4c. Five consecutive failed attempts:** The system locks the account for 15 minutes and displays "Account locked — try again later". The use case ends in failure.
- **3a. Server unreachable:** The client displays "Cannot connect to server". The use case ends in failure.

## UC: Manage Accounts & Permissions

**Primary actor:** System Administrator
**Goal:** Create, update and deactivate user accounts and assign each account a role.

### Details
**Pre-conditions**
1. The System Administrator is logged in.

**Post-conditions — success**
1. The account change is saved in the database.
2. The change is recorded in the audit log with the timestamp and the administrator's identity.

**Post-conditions — failure**
1. No account data is changed.

### Flow of Events (main flow — create account)
1. The System Administrator opens the account management screen.
2. The system displays the list of user accounts with their role and status.
3. The System Administrator selects "Add user".
4. The System Administrator enters a username, an initial password, a full name and selects a role from the closed list (System Administrator, Logistics & Resources Officer, Dispatcher, Field Commander, Field Crew Member).
5. If the role is Field Commander or Field Crew Member, the System Administrator links the account to an existing personnel record.
6. The System Administrator saves the account.
7. The system validates the data.
8. The system stores the account with a salted password hash and displays a confirmation.

### Extensions
- **3a. Edit an existing account:** The System Administrator selects an account, changes its details or role, and continues from step 6.
- **3b. Deactivate an account:** The System Administrator selects an account and chooses "Deactivate". Continues at 3b.1.
  - **3b.1.** If the user is a Field Commander or Field Crew Member currently reserved for an Active task, the system rejects the action and displays "User is reserved for an active task". The use case ends in failure.
  - **3b.2.** If the account is the last active System Administrator, the system rejects the action and displays "At least one active administrator is required". The use case ends in failure.
  - **3b.3.** Otherwise the system asks for confirmation, deactivates the account and ends any open session of that user.
- **5a. No matching personnel record:** The system displays "Personnel record not found — load it via Load Initial Data first" and returns to step 4.
- **7a. Username already exists:** The system displays "Username already taken" and returns to step 4.
- **7b. Password does not meet the policy (at least 8 characters, letters and digits):** The system displays the policy and returns to step 4.
- **8a. Database error while saving:** The system rolls back, displays "Save failed — please retry" and returns to step 2.
